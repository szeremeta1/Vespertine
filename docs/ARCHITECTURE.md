# Architecture

## From file to DAC

```
file ─▶ SFBAudioEngine / FFmpeg ─▶ [DoP / DSD→PCM wrapper] ─▶ [CUE region] ─▶ AVAudioConverter ─▶ ring buffer ─▶ HAL IOProc ─▶ DAC
         (libFLAC, TagLib…)                                                  Float32, SRC only        lock-free     C, no locks,
                                                                             when rates differ        SPSC          no allocation
```

1. **Probe.** `SourceOpener.probe` opens the file and reports its true `SourceFormat`: codec, lossless/lossy/DSD, rate, bit depth and channels.
2. **Plan.** `FormatPlanner.plan` (pure and unit-tested) combines the source with the device's `DeviceCapabilities` (discrete nominal rates, physical formats, DoP opt-in) and the per-device `RatePolicy`. It produces an `OutputPlan`: device rate, physical bit depth, PCM or DoP, and whether SRC or DSD→PCM conversion is needed.
3. **Configure.** `OutputSession` takes hog mode only in exclusive mode (shared is the default, so the device can stay the Mac's sound output), sets the stream's physical format (preferring integer at the planned depth), sets and verifies the nominal rate, ensures a Float32 virtual format, and installs `nrt_device_ioproc`. `DeviceRestore` remembers each device's format before the first change, so it can be put back when Vespertine quits.
4. **Decode.** The engine thread pulls decoded audio through `AVAudioConverter`. With equal rates the converter only changes the sample format; integer PCM up to 24 bits maps exactly into Float32, which a unit test verifies sample-for-sample. With different rates it uses `AVSampleRateConverterAlgorithm_Mastering` at maximum quality.
5. **Render.** The IOProc copies from the ring buffer into the device buffer. Gain of exactly 1.0 with no equalizer is a straight copy. Otherwise the equalizer (a preamp and up to 20 biquads per channel, transposed direct form II) and the gain are applied in double precision, with TPDF dither at the DAC's word length. DoP is always passthrough.

The equalizer's settings reach the I/O thread through a triple buffer (`nrt_context_set_eq`): the engine thread fills a spare bank and swaps it in, and the I/O thread picks up the newest at the start of a slice, so neither side waits and an edit is heard within one device buffer instead of after the 20–30 s in the ring. The sections are designed for the device's actual rate (`EQPreset`, from the Audio EQ Cookbook). A preset that changes nothing counts as none, so playback stays bit-perfect; integer mode is skipped while one is on. DoP, bitstream and macOS-rendered Atmos never pass through it, and the interface says so: `EqualizerStatus` (`eqActive`, `reason`) drives the note and dimmed curve in the Equalizer window, and `SignalPath.bypassedEqualizer` the "bypassed" row of the signal path.

Every decoder is wrapped in `GuardedDecoder`, which calls it through `CVespertineGuard` (Objective-C++). A C++ or Objective-C exception thrown inside a codec library, such as Monkey's Audio seeking in a truncated file, becomes an ordinary "won't play" error instead of ending the process.

## DSD

DSF and DSDIFF open through FFmpeg at any rate from DSD64 to DSD512 (SFBAudioEngine's readers stop at DSD128, and its DSD→PCM at DSD64). For DoP, `RawDoPDecoder` reads the raw DSD bytes (`nff_read_dsd`; DSF is planar and LSB-first, DSDIFF interleaved and MSB-first) and packs 16 bits per channel into each 24-bit frame with alternating 0x05/0xFA markers, so the DAC runs at a sixteenth of the DSD rate (176.4 kHz for DSD64). An odd last byte per channel is padded with DSD silence (0x69) into a whole frame; DoP 1.1 doesn't cover half a frame. DoP is planned only when the DAC is marked DoP-capable and supports that carrier rate; otherwise FFmpeg converts DSD to PCM at an eighth of the DSD rate and the planner resamples as needed.

DoP frames are passthrough, so meters and the spectrum can't read them as PCM. With `nrt_context_set_dop`, the render context reads the DSD bits in each frame instead: a triangular window over the current and previous frame's 16 bits (a sinc² decimation by 16) gives a level for the meters and the spectrum tap, and the inspector's spectrum stops at 20 kHz for DoP. The frames themselves are never modified; a test checks they come out bit-identical.

## SACD images

An SACD image (`.iso`) is read in place (`SACDImage`, `SACDDecoder`), whether it stores plain 2048-byte sectors or whole 2064-byte physical ones (12 bytes of header before each sector's 2048, 4 after). The Master TOC is at sector 510, with copies at 520 and 530; the first copy whose every area TOC can be read is used (or, when all are damaged, the one that leads to the most areas). It points to the 2-channel area's TOC and the multichannel one's (a disc can have either or both, and each area TOC is stored twice); each area TOC holds the track list (`SACDTRL2`: start and duration as time codes of 1/75 s frames, on the same clock as the audio frames' own time codes, which start at 00:00:00 with the first track usually at 00:02:00), the track text (`SACDTTxt`) and ISRCs and genres (`SACD_IGL`). A track runs from its start to the next track's start, so a pause between tracks stays with the one before it and the tracks join without a gap; the last one ends with its duration, within the area's playing time. Track times that can't be right (seconds or frames out of range, a track starting before the one before it) make that area unreadable rather than guessed at. The library stores each track as `<image>#2ch-3` or `#mch-3` with its stretch of the area in DSD samples (`cueStartFrame`), and the two areas are two copies of the album whose tracks match as one song's stereo and surround versions (`LibraryCopies`, `TrackVersions`). `PlayableItem.sacdArea` tells `SourceOpener.probe` which area to open.

Audio sectors carry packets of frames: `SACDFrameReader` reassembles them and finds a frame by binary search over the sectors' frame time codes. It hands back only whole frames: a DST frame once it has the number of packets its header declares, a plain one at exactly 4704 bytes per channel. Plain frames are DSD bytes interleaved by channel, MSB first, as in DSDIFF. DST frames are decoded to the same bytes by `vespertine_dst.c`, a standalone copy of FFmpeg's DST decoder (LGPL-2.1-or-later) changed to return the DSD rather than convert it, so DST areas can go out as DoP, and to reject frames that can't be valid (a short stored frame, tables running past the frame, out-of-range filter coefficients, more than 7 bits of arithmetic code left unread, as the reference decoder checks). DST has no checksum, so damage that still decodes can't be told from music. A frame that is missing, incomplete or rejected plays as DSD silence, and `SACDSource` counts it: the engine copies the count to the track's `SignalPath.concealedFrames`, which turns BIT-PERFECT off ("DAMAGED FRAMES SILENCED"). A long run of them stops the track with an error. The DSD then takes the existing paths: `RawDoPDecoder` packs it (any `RawDSDSource`: FFmpeg's DSF/DSDIFF reader or an SACD area), and `SACDPCMDecoder` feeds it to FFmpeg's `dsd_msbf` decoder, the converter DSDIFF files go through. A track's PCM starts one frame early to prime the converter's filter, so consecutive tracks come out exactly as the area converted in one piece. Tests compare both paths against DSDIFF files of the same DSD, bit for bit; the fixtures are synthesized SACD images with DST frames from a small encoder in `Tests/VespertineTestSupport`, laid out like real discs.

## Format badges

`FormatMark` (VespertineLibrary) names a track's or album's format for badges: Dolby Atmos (with what carries it), Dolby TrueHD, Dolby Digital Plus, Dolby Digital, DTS-HD Master Audio, DTS:X, DTS, DSD64–DSD512, Hi-Res Lossless or Lossless. The badge is plain text in the app's own style. Dolby's and DTS's logos are trademarks licensed only with certified products, and Vespertine's TrueHD and DTS decoders (FFmpeg) are not licensed, so the logos aren't used.

## Gapless and format changes

When the current item has been fully decoded, the engine asks `nextItemProvider` for the next one (thread-safe via `QueueMirror`).

- If the new plan is device-compatible (same rate, depth, mode and channels), decoding simply continues into the same ring buffer, and a segment marker records where the new track begins.
- Otherwise the ring buffer drains, the device plays out its own buffer, and the session is reconfigured. That short gap is unavoidable, and every player has it.

Track changes are reported when the new segment becomes *audible*, not when it is decoded.

A queue change (shuffle, repeat, edits) never touches the audible track. If the next track has already been decoded into the ring, `nrt_ring_rewind` takes that look-ahead back, but only when it is still well ahead of the reader (the larger of 250 ms and four I/O buffers). The engine then asks `nextItemProvider` again. When the look-ahead is too close to be taken back safely, it plays, and the new order applies from the track after it.

## DTS CDs

A DTS CD (or DTS-WAV) stores a DTS bitstream as 16-bit stereo PCM, usually in 14-bit words. Played as PCM, it is full-scale noise. When `SourceOpener.probe` opens a 16-bit stereo 44.1/48 kHz lossless file, it looks in the first 16,384 frames for two consecutive DTS frames, each with a valid core header and each where the one before it says (`ndts_find_stream`): a sync word on its own is just two sample values, which ordinary music has now and then. If it finds them, it wraps the file's decoder in `DTSDecoder`; if FFmpeg then finds no DTS frames after all, the file opens as the PCM it looks like. That decoder feeds the words, as stored, to FFmpeg's `dca` parser and decoder (the `CVespertineDTS` shim over `Vendor/FFmpegDCA.xcframework`, built by `scripts/build-dts-decoder.sh` with only the DTS, TrueHD/MLP, Dolby Digital (Plus) and DSD decoders). Output is Float32 in the stream's own channel order, with a layout from its channel mask.

Positions stay in the carrier's frames: a DTS CD holds one 512-sample frame per 512 carrier frames. So CUE indexes, seeks and durations are unchanged. Carrier frames before the first sync word are silence. A seek re-syncs a little before the target and drops the surplus decoded frames. The source is reported as lossy "DTS" with its real channel count, so the planner routes it as surround or Spatial Audio. A test checks the decode of a real DTS CD against FFmpeg's, bit for bit.

## Dolby, TrueHD and DTS-HD

- **Dolby Digital / Dolby Digital Plus** decode through macOS's licensed decoders (`.ac3`/`.ec3` are routed to the Core Audio decoder, which the MP3 decoder would otherwise claim by extension). A Dolby Digital Plus file carries Atmos objects (JOC) when Core Audio lists `ec+3` formats for it (5.1.2 up to 9.1.6). The codec is then "Dolby Atmos".
- **Dolby Atmos.** macOS doesn't expose object rendering through its public decode APIs: AudioConverter, ExtAudioFile and AVAssetReader all give the 5.1 bed with silent heights, which was checked on Apple's Atmos sample stream. So by default `SystemRendererSession` hands the untouched Dolby Digital Plus frames (AVAssetReader, compressed) to `AVSampleBufferAudioRenderer` on the chosen device, with a render synchronizer for position, pause and seek. macOS renders the objects for the output, as Apple Music does. With `atmosBySystem` off, the bed plays through Vespertine's own engine.
- **DTS / DTS-HD MA / Dolby TrueHD** in `.dts`, `.dtshd`, `.thd`, `.mlp` and `.mka` decode through FFmpeg (`CVespertineFF`, `FFmpegDecoder`). Lossless ones are reported as PCM with their bit depth. A test checks TrueHD decodes identically to the 24-bit source it was encoded from.
- **TAK and the audio of Matroska / WebM** (`.tak`, `.mka`, `.mkv`, `.webm`) go through the same FFmpeg path. `FFmpegDecoder.describe` names the codec from FFmpeg's codec name and profile (FLAC, ALAC, WavPack, APE, TTA, TAK, PCM lossless (tested exact for all but APE and TAK-in-Matroska); AAC, xHE-AAC, MP3, Vorbis, Opus lossy), and `append` in `vespertine_ff.c` carries every integer width FFmpeg's lossless decoders use (left-justified 32-bit integers, 16-bit, 8-bit) to Float32, exact to 24 bits. A file with several audio streams is read stream by stream: `nff_open_stream` takes the container's stream index (`PlayableItem.audioStream`), `FFmpegDecoder.audioStreams` lists them, and the library scanner lists a track for each (`<file>#audio-<n>`, `AudioStreamRef`). Matroska stores times in milliseconds, so a seek lands within 1 ms (48 samples at 48 kHz) of its target. The FFmpeg build is `scripts/build-dts-decoder.sh`; FFmpeg's DST decoder isn't in it (it returns PCM; `vespertine_dst.c` is the DST path).
- **DSD in WavPack** (`WavPackDSD.swift`): SFBAudioEngine's prebuilt libwavpack is compiled without DSD, so `scripts/build-wavpack-dsd.sh` builds WavPack 5.8.1 with `ENABLE_DSD` into `Vendor/WavPackDSD.xcframework`, every global symbol prefixed `vtwv_` so it can't meet SFB's copy. `WavPackDSDSource` opens the file with `OPEN_DSD_NATIVE` through a `PlaybackFile` (network cache aware) and is an `InterleavedDSDSource`: libwavpack hands back one DSD byte per channel per sample, most significant bit first whatever the source file's order (a DSF's LSB-first bytes are reversed back by the library, as `wvunpack --dff` shows). `RawDoPDecoder` packs it as DoP and `SACDPCMDecoder` converts it like DSDIFF, so both are the paths DSDIFF already takes. A short or damaged file is an error, not a shorter track.
- **Embedded CUE sheets** (`EmbeddedCue`): with no `.cue` beside it, a FLAC's `CUESHEET` tag (a whole sheet, titles included) or `CUESHEET` metadata block (CD-DA tracks in samples, kept exact in `CueSheet.Entry.startSample`) splits the file into `<file>#<n>` tracks like an external sheet. A rescan treats them like a disc image's tracks: unchanged when the file is.
- **Formats nothing here decodes** (`UndecodedFormat`): AC-4 and MPEG-H are found by sync word (`.ac4`: `0xAC40/41`, `.mhas`: `0xC001A5`) or by an MP4's first sound sample entry (`ac-4`, `mha1`, `mha2`, `mhm1`, `mhm2`) and refuse to play with a plain reason; the library keeps them under their name. MQA (tags `MQAENCODER`; or the 36-bit word `0xBE0498C88` in bit 16 of left XOR right of 24-bit stereo samples, read through a decoder of its own) and Auro-3D (the release's name only: the PCM carries nothing a player can read) play as PCM; `Track.formatMark` shows a text badge and the signal path's decoder line says so.

## Bitstream (IEC 61937)

Receiver bitstream is experimental, untested on real receivers and multichannel USB DACs (one Sony TV over HDMI has been tested: see docs/DEVICES.md); reports wanted. The tests below validate the carrier, not a receiver.

On outputs marked as having a receiver (`bitstreamDeviceUIDs`), Dolby and DTS-CD sources plan as mode `.bitstream`: exclusive, exact rate, integer ≥ 16-bit, no gain. `BitstreamDecoder` wraps Dolby Digital frames in 1536-frame bursts at the stream's rate (Pd in bits). It groups Dolby Digital Plus frames into six-block bursts of 6144 frames at four times the rate (Pd in bytes, so HDMI only). DTS CDs go out as stored. The carriers are checked with FFmpeg's S/PDIF demuxer, which decodes them identically to the original files. A gapless transition into an Atmos track that macOS renders drains the ring first, then hands over. The framers check their input (`BurstError`): a frame that doesn't parse, a payload too big for its burst, or a Dolby Digital Plus burst of other than six blocks is refused, and goes out as silence of the same length, counted as damaged frames. A short last Dolby Digital Plus burst at the end of a stream goes out as silence too, uncounted.

## Integer mode

With `integerMode` and exclusive access, plain PCM that needs no processing plans with `integerSamples`: no resampling, Spatial Audio, downmix, digital volume or ReplayGain, on a device with a non-mixable Int32 physical format. `OutputSession` switches the physical format to non-mixable Int32; setting only the virtual format is accepted but ignored by USB Audio Class DACs such as the FiiO K11. The converter then decodes straight to Int32. The ring carries those words in its float slots, and the IOProc copies them as integers, including ones that would be NaN as floats, while meters read them as integers. So 32-bit sources are bit-perfect. The device is put back on mixable Float32 when the session ends.

## Match 16-bit sources

With `matchSixteenBit`, `FormatPlanner.matchSixteenBit` sets `physicalBitDepth = 16` on a plan for integer 16-bit PCM at its own rate and channel count (no resampling, downmix or Spatial Audio, never DSD, DoP or bitstream), when the device lists an integer 16-bit physical format with enough channels at that rate. The engine adds its conditions: exclusive access, not the built-in output, no digital volume, EQ or ReplayGain. `DeviceControl.apply` then picks the 16-bit physical format, and the I/O proc renders Float32 as usual, which carries every 16-bit sample exactly, so integer mode isn't used. The plan records `sixteenBit` (`.requested` or `.noMode`), and `SignalPath.sixteenBitNote` reports what the device actually reads back, including a device that ignored the request. 16-bit and deeper plans aren't device-compatible, so a change between them reconfigures the device; when the session ends, the device goes back to its full depth.

## Loopback self-test

`LoopbackRunner` (VespertineAudio) runs a separate `PlaybackEngine` with settings that turn off everything that could change the samples: EQ, digital volume, ReplayGain, Spatial Audio, bitstream and DoP, with the rate matched to the source. It runs on a virtual output device only (`LoopbackGuard` refuses others).

For each case it does the following:
1. Writes the `LoopbackSignal` to temporary WAVs, so the real decoder runs.
2. Records the device's input with `LoopbackRecorder`. Its IOProc (`nrt_capture_ioproc`) is real-time safe: it copies into the lock-free ring and counts `mSampleTime` discontinuities and overflows.
3. Trims the capture and hands it to `LoopbackAnalyzer` (VespertineAnalysisCore, pure Swift, also tested on Linux).

`LoopbackResultStore` keeps results in `loopback-results.json`, keyed by device, case, settings, macOS and app version. The app's `LoopbackTest` model shows the newest result for the playing format as an informational signal-path step. `SignalPath.isBitPerfect` never reads it. See [LOOPBACK.md](LOOPBACK.md).

## Output device

With a specific output chosen (`EngineSettings.deviceUID`), the engine never substitutes another device. If that device isn't listed, or won't start, when playback begins, the item is parked and the engine waits for it (`waitingForDevice` in the snapshot) for up to 60 s. It re-checks on every Core Audio device-list change and twice a second, and starts playback as soon as the device is back. If the device disappears mid-song, it waits the same way. This covers AirPods Max, whose Core Audio device is removed while they're off your head and re-published a few seconds after they're back on, often after their "play" command has already arrived. Pause cancels the wait. With *System Output* chosen, the engine follows the Mac's default output as before.

The device list shows devices with output channels only. Core Audio announces a new device (`kAudioHardwarePropertyDevices`) before every device has published its output streams: AirPods Max on USB-C join with none. So `DeviceMonitor` listens to `kAudioDevicePropertyStreams` and `kAudioDevicePropertyStreamConfiguration` (output scope) on every device without output, re-checks a device that just joined four times a second for 15 s in case no notice comes, and reports a device change once it has output. Without that, such a device stayed off the list until the Mac's default output changed.

### Switching and skipping

- **Instant silence.** Skip, seek, pause, stop and a change of output set `nrt_context_set_muted` from the caller's thread: the IOProc plays silence and takes nothing from the ring. The old song stops at once even while the engine thread is busy (a network read can take seconds, and the ring holds 20–30 s). The engine clears the mute when it starts or resumes playing; because nothing was consumed, a pause or output change resumes exactly where it went quiet.
- **Output changes keep the file open.** `restartFromCurrentPosition` hands the song's open decoder to the restart (`carried`), which seeks it back to the playback position when the new output needs the same kind of decoding (PCM stays PCM). Only the output session and converter are rebuilt, so a switch takes a few hundred milliseconds even on a busy share, instead of reopening and re-analysing the file.
- **Commands go first.** The start-up prefill stops as soon as another command is waiting, several output changes in one batch restart playback once, and a retry for an output that isn't ready reuses the file already probed.
- **Probing is small.** FFmpeg-opened files (DTS, TrueHD, Matroska, DSD) are analysed from their first 256 KB / 0.1 s; their headers and first frames describe them fully.

## Bit-perfect definition (`SignalPath.isBitPerfect`)

A path is marked bit-perfect only when all of these hold:

- The device profile can be bit-perfect (i.e. not Bluetooth or AirPlay).
- The device is held exclusively, or (shared mode, PCM only) no other process is currently sending audio to it (Core Audio process objects, checked about once a second).
- No Spatial Audio rendering or downmix.
- No software gain is applied (neither ReplayGain nor digital volume).
- The decoder hasn't replaced any damaged frames of the track with silence (SACD images).
- For PCM: the source is lossless, it isn't resampled or converted from DSD, the source is at most 24-bit (32-bit with integer mode, which skips the Float32 step), and the device's physical format can hold it (an integer format at least as deep as the source, or 32-bit float).
- For DoP: the device is held exclusively (DoP always takes it, whatever the exclusive setting, and doesn't play without it), and the carrier runs at the planned rate with at least 24 bits.

## Visualizer

The visualizer window reads its own tap, a stereo copy of the samples the meters read (after room correction, the equalizer and gain, scaled back by 1 / gain), written by the I/O proc only while a window shows it. The reader takes the newest frames and drops what it missed, so it can't hold up the I/O thread, and the output is bit-identical with the tap on or off. Analysis runs on a thread of its own and drawing in Metal. See [VISUALIZER.md](VISUALIZER.md).

## Library

The library is SQLite via GRDB:

- The `track` table has generated sort and grouping columns (lists order by them through `vesperSort`, an SQL function that folds case and accents, since SQLite's `lower()` folds ASCII only), FTS5 search (accent-insensitive; a query with Han, kana or Thai matches any part of a field instead, since the index keeps such runs whole) and JSON columns for custom tags.
- Albums are aggregated in SQL rather than stored. An album key can hold several copies of the album (`LibraryCopies`, `AlbumCopies.swift`): its tracks are split by album folder (the one above disc and layer folders such as `CD 01`, `Digital Media 02`, `Stereo`, `Multichannel 5.1`, `VIDEO_TS`; a disc image is its own folder), by layout (stereo and mono, each surround channel count, Dolby Atmos), and, only where one folder holds the same songs twice, by top-level files against disc folders, then by format, then by repeat. The edition is the last bracket of the folder name. Songs are matched across copies one track per copy, strongest first: the same MusicBrainz recording or ISRC; else the same title, exactly or without a mix, master, layout or edition label ("(2021 mix)", "(5.1 mix)", "- 2009 Remaster"), within 6 s or 4 % in length, with the same disc and number as a tiebreak; else the same disc, number and length (within 2 s) with titles that start alike, unless the longer one names another recording (live, demo, acoustic, take…). Unmatched tracks are songs of their own (bonus tracks). Per-album choices (`albumCopyChoice`: a copy, or bundled) and preferred copies (`preferredCopy`) are library state. Unbundled, the queue plays exactly the tracks it was given; bundled, `TrackVersions.choose` picks each song's copy for the output when it's queued and again when the output changes. A favorite is the copy hearted, and is spread to every copy of the song only where the album is bundled. The env-gated `CopiesReportTests` reports what this makes of a real library database, opened read-only.
- `LibraryScanner` is incremental (it compares size and modification time), splits single-file CUE albums into region tracks, and flags vanished files as missing instead of deleting them: they disappear from every list, playlists included, and come back with their analyses if the files return. A scan interrupted by a dropped share marks nothing missing.
- Moved and renamed files (a library manager such as Lidarr reorganizing a share) are recognized at the end of each scan. `reconcileMovedTracks` pairs each missing track with a new one of the same size, duration and title (the same file, moved). For a file whose tags were rewritten on the way, it instead uses the same title, artist, track, disc, format and duration. A pair must be unambiguous on both sides. The new entry takes over the old one's playlist entries, play count, rating, date added, tag history and, for an unchanged file, its analysis. The stale entry is dropped, and the play queue is repointed at the new files. When a song fails to play because its file is gone, its source is rescanned at once (at most every two minutes), even during playback.
- Genres are normalized in `Genres` (case, accents, hyphens, slash order, ID3 numbers, localized Apple names) for browsing, filters and search.
- Every page has its own filter (`LibraryFilter`): format, sample rate, bit depth, channels, analysis verdict, genre, decade, artist and source, plus the 24-bit, 88.2 kHz-and-up, multichannel and favorites conditions. Choices within one facet widen the match and facets narrow it. The album query also aggregates every format, rate, depth, layout, verdict and source among an album's tracks (`FilterFacts`), so album pages filter without reading tracks. An album matches a facet when any of its tracks does. Playing or shuffling a filtered album page plays those albums' songs that pass the per-song facets (format, layout, verdict, source, favorites); when a song has several versions, only the passing versions are candidates. A page opened from a filtered one (an artist from Artists, a genre from Genres) starts with its filter.
- Smart playlist rules compile to SQL; sample rates are entered in kHz, and a rule without a usable value matches nothing.
- `TagWriter` writes tags with TagLib through SFBAudioEngine. Beforehand it takes an APFS clone of the file (free on the same volume) and stores the previous tags in `tagHistory` for revert.

## Multichannel and Spatial Audio

Channel-for-channel output is experimental, untested on real receivers and multichannel USB DACs (one Sony TV over HDMI has been tested: see docs/DEVICES.md); reports wanted. Routing has automated tests (every sample of the test files carries its channel's number, so each output's source and bit-exactness is read from what the device got: `MultichannelDeviceTests`), a six-channel aggregate-device check, and an opt-in loopback through the real engine and Core Audio to BlackHole 16ch (`VESPERTINE_MULTICHANNEL_LOOPBACK=1`, `MultichannelLoopbackTests`: 3 to 12 channels, 44.1 to 192 kHz, 5.1 DSF and SACD, and Spatial Audio rendered on the I/O thread).

`FormatPlanner` sends every channel to devices that can carry them (following the speaker layout from Audio MIDI Setup, and counting an HDMI receiver's channel capacity even in 2-channel mode), downmixes by channel layout on stereo devices, and on AirPods and Beats renders the channels with Apple's spatial mixer (`AUSpatialMixer`, head tracked or fixed) inside the I/O callback, through a C hook, so head tracking responds instantly.

On a device with as many outputs as the file has channels and no speaker setup, the plan's `routeLabels` name the outputs in the standard order for the count (L R C LFE Ls Rs …), and the converter gets an explicit channel map (`ChannelLayouts.discreteMap`) instead of mixing by layout: each channel goes, unmixed, to its own speaker's output, else the nearest single one (a 5.1's back pair on Ls/Rs), else an output left over, which is then named after it (2.1's LFE, LCRS's centres, 7.1 wide's front centres, 5.1.2's heights). Channels with no speaker names are taken in WAV order (`ChannelLayouts.wavOrderLabels`: 7.1 as FL FR FC LFE BL BR SL SR, so the side pair still reaches Ls/Rs). Matched by layout, the converter dropped speakers the standard layout lacks, put a side pair on the back pair at -3 dB, lowered a whole mix it folded a pair into, and played files with no speaker names as silence.

Above 8 channels there's no standard order: the outputs are numbered and each channel goes to its own, in the file's order (the converter played unnamed 12- and 16-channel files as silence). Unnamed files of 10, 12, 14 and 16 channels are taken as FFmpeg's default layout for the count (5.1.4, 7.1.4, 9.1.4, 9.1.6) wherever positions matter: on headphones Apple's spatial mixer heard only the first two channels of a numbered layout. The same WAV-order convention applies on headphones as on speakers, so a channel lands on the same speaker on both.

On a configured speaker setup (Audio MIDI Setup, an HDMI receiver's own layout) every channel with a speaker of its own also goes out unmixed through an explicit map (`ChannelLayouts.speakerMap`), with setup and source compared in one surround convention (a setup naming its back pair Ls/Rs beside Lsd/Rsd is read the WAVE way). Only a real fold (7.1 into a 5.1 room, 7.1.4 into 7.1) mixes, and it's Vespertine's own (`OutputSession.speakerFold`, BedRouter): channels with their own speaker untouched, the others on the nearest one at -3 dB (ITU-R BS.775), a missing centre equal-power on L and R. Matched by layout, Apple's converter played unnamed files as silence on any speaker setup, put a WAV 7.1's back pair on the side speakers, played 5.1.2 into 5.1 as silence and dropped speakers it had no place for. A driver's placeholder layout (channel n labelled n, as BlackHole reports before anyone configures speakers) isn't a setup (`ChannelLayouts.isPlaceholder`): read as one, an unconfigured 8-channel output was a front-centres 7.1 room and a 4-channel one a 3.1.

## Network shares

- `NetworkVolume` mounts with NetFS: soft, read-only by default, hidden from the Finder sidebar, in `/Volumes`. Current macOS refuses mounts inside an app's Application Support folder (protected app data), so mounting there would work once and never again.
- Passwords are internet-password items in the **login** keychain (queried explicitly: an app's plain SecItem calls go to the data-protection keychain, where Finder's share passwords never are).
- `NetworkShareManager` heals connections: it reconnects on launch, wake and network changes, remounts a share that disappeared, force-remounts one that is still listed but no longer answers, and, with Settings → Library → Scan for new music automatically on (off by default), rescans connected shares every 30 minutes (and after the server's analysis run), never while music plays from them. File-system events don't cross the network; these rescans are how additions and deletions on the server appear. That setting also governs the folder watcher and the scan at launch (`LibraryStore.automaticScanning`); Rescan, Rescan Library and a share's first index always run, and so does Analyze Library, while *Analyze new music automatically* (also off by default) alone starts analysis after a scan or at launch and syncs the servers' results every 5 minutes. Installs that predate the opt-in are put to off once (`AppSettings.migrateAutomaticWorkToOff`).
- Playback from a share buffers more before starting, holds in silence and resumes exactly where it stopped if reads stall, and gets priority over caching and analysis. It resumes once 5 s are buffered again; each stall within a minute of the last doubles that, up to 20 s, so a link only just fast enough gets a few longer holds rather than a stop every few seconds. Any file on a volume macOS doesn't mark local counts, not only those of shares set up in Vespertine.
- A track read live from a share is decoded on a thread of its own, about 8 s ahead (`ReadAheadDecoder`). A read stuck on the share holds up only that thread: the engine takes what's decoded (`.noDataNow` to the converter when there's nothing yet) and keeps answering pause, skip, seek and output changes. Unit tests check the output is byte-identical to direct decoding, through seeks, DoP marker joins and the move to the local copy.
- While a song streams from a share and its buffer is under a third full, cache copies pause between reads (`NetworkCache.yieldsToPlayback`) and carry on once it's two thirds full: on a link little faster than the music, a copy alongside took half of it.
- The output ring holds about 20–30 s of audio: `OutputSession.ringFrames` is a power of two within a 96 MB budget, never under 5 s. A share whose server is busy (on a loaded HDD pool, a single read can wait several seconds) never drains it. The cache copies the playing track first, 2 s after it starts. Once the copy is complete, `PlaybackEngine.reopen` opens it at exactly the decoder's frame and swaps it in under the converter, so the rest of the track is read locally. A unit test checks the result is byte-identical to continuous decoding for FLAC and WAV. This happens only where a seek can't change the output (lossless PCM and DoP). Lossy decoders and DSD→PCM carry state across a seek, so those tracks finish from the share. `EngineSnapshot.readingFromShare` shows which source is in use.
- The share health check doesn't count a slow answer as a dead mount while the cache or playback is still receiving data (a remount would cut off what's playing).
- A scan gives each request to its source (is it there, list a folder, read a file) 90 s once it starts (`LibraryScanner.responseTimeout`). A share that stops answering blocks such a call until the system gives up, which can be never; past the deadline the scan stops with `ScanError.notResponding`, marks nothing missing and leaves the source's last-scanned time as it was, and the app keeps the reason beside the source in the sidebar and in Settings › Network until a scan of it finishes. Rescan no longer joins whatever scan is running: one that hasn't heard from its source for 20 s (`stallLimit`) is cancelled (it writes nothing more) and a new one starts, and one still moving is followed by another, so a file added after it listed its folder is found. Scans the app starts by itself still join the running one. Tests: `StuckScanTests`.

## File analysis

The analysis core lives in `Packages/VespertineAnalysis` (plain Swift and Foundation): spectra (Accelerate on Apple platforms, a portable FFT elsewhere, tested to agree), the forensic measurements, a chunk-independent sample accumulator and the verdicts. The app decodes with SFBAudioEngine and feeds it. On a server, `vespertine-analyze` decodes with ffmpeg and feeds the same core, writing `<share>/.vespertine/analysis.jsonl`; the app imports matching records (path, size, modification time) and leaves that share's files to the server. See [ANALYSIS.md](ANALYSIS.md).

## Known limits and roadmap

- **Integer mode** needs exclusive access and a DAC with a non-mixable Int32 format. Elsewhere Vespertine renders Float32, which is exact up to 24 bits.
- **Object audio.** Atmos in Dolby Digital Plus is rendered by macOS. Atmos in TrueHD and DTS:X play their lossless channel bed; their objects are not rendered, and macOS gives apps no way to send TrueHD or DTS-HD MA over HDMI (no high-bit-rate passthrough).
- **No decoder** for Dolby AC-4, MPEG-H 3D Audio (`UndecodedFormat`: named in the library and when played, not decoded), MQA unfolding or the Auro-3D height channels; MQA and Auro-3D files play as the PCM they hold. xHE-AAC, APAC and Opus multichannel have fixtures and play through Core Audio / libopus / FFmpeg.
- **Resampler.** SRC uses Apple's mastering-quality converter. libsoxr is a candidate alternative.
- **DoP support** can't be detected from the device, so it is opt-in per device.
- **AirPods Max over USB-C.** macOS keeps the AirPods on their *Bluetooth* Core Audio device even when audio flows over the cable. Bluetooth stays connected as the control link, and the cable can't be used without it. The HAL exposes no "USB" property for this, so Vespertine treats the path as USB-C lossless when the AirPods' `AirPods Max USB Audio` interface is present in the IORegistry. (Measured on hardware: output latency is 480 frames / 10 ms, as expected of USB.) The device also lists a 24 kHz rate, but that is the mono hands-free format, and the planner ignores rates that can't carry the source's channel count. Reference equalizer presets for AirPods Max USB-C (1st generation) and AirPods Max 2 are offered in the preset list but never chosen automatically, so the AirPods stay bit-perfect until one is picked for them.

## Transitions

Crossfades and fades between songs, off by default (details: [TRANSITIONS.md](TRANSITIONS.md)). With the master switch off, none of what follows runs.

- **Planning.** While the last crossfade + 16 s of a song are decoded, the engine asks `nextItemProvider` early, probes and plans the next song as `advance` would, and `TransitionPlanner.decide` picks gapless, a cut (DoP, bitstream, Atmos by macOS, integer, 16-bit), a dip (another rate or channel count) or an overlap.
- **Mixing** happens on the engine thread before the ring (`TransitionMixer.swift`): two `Decoding`s (EngineDecoding.swift), each with its own converter and ReplayGain, mixed a chunk at a time, the outgoing song's silent tail and the incoming song's silent head trimmed. A dip ramps the outgoing song's last second before the ring, then the usual drain and reconfigure, then ramps the next song's first second.
- **Segments.** The incoming song's segment starts at the overlap and becomes audible (trackStarted, Now Playing) at its middle. `replanUpcoming` rewinds a baked overlap to its start and decodes the outgoing song again when that is exact; otherwise the overlap plays as mixed.
- **Real time.** `nrt_context_fade` ramps the existing gain stage for play, pause, stop, skip and seek; idle it is never entered. It never touches DoP, passthrough or integer words.
- **Smart Mix.** `TransitionProfile` (VespertineAnalysisCore, plain Swift) describes each end of a song: silence, a fade and its confidence, BS.1770-4 loudness, the end's type, a steady beat. The library stores it (`transitionProfile`, invalidated like `analysis`) from the file-analysis pass or a server's index; the engine reads it through `transitionProfileProvider`, or measures the ends just in time (`EdgeScan`). `SmartMixPlanner` turns the two ends into a `SmartMix` (into a fade, quick cut, trimmed blend, segue = gapless, or a plain crossfade), and `Crossfade` mixes it with a loudness match and a lookahead limiter that holds 5 ms back inside the overlap only.
- **Skip crossfade.** `nrt_ring_peek` (producer side) copies what the ring holds a quarter second ahead of the reader; `nrt_ring_rewind` takes the ring back there; the copy is mixed with the next song's start and written in its place.
- **Gaps and playlists.** A gap is written as silence ahead of the next song (`gapOwed`, kept safe from queue edits mid-gap). A playlist's own transitions travel in `TransitionContext.override` on each queued item; the master switch rules over them.
- **Transitions first.** While the switch is on and the policy says so, `FormatPlanner` converts DSD to PCM (`dsdToPCMForTransitions`), integer and 16-bit modes aren't planned, and a song at another rate is planned at the session's rate (`resampledToSession`) when that lets it blend.

## Speaker groups

A group (`SpeakerGroup`, saved in `Speaker Groups.json`) is played through a private Core Audio aggregate that `GroupAggregate` describes and `GroupAggregateDevice` creates: the clock leader is the time base, every other member has drift compensation at the highest quality (unless members share a hardware clock domain). `GroupMemberSession` holds and configures each member at the song's rate and reads the format back from the member, never from the aggregate (whose streams report the aggregate's rate even while a member resamples). `OutputSession` then runs its usual multi-buffer I/O proc on the aggregate. A song's channels reach the aggregate through `PositionRouter` (equal-power panning by speaker angle, ITU-compatible special cases); the delay, level and polarity of each speaker, and the headroom for their boosts, join the room-correction chain on the I/O thread (`GroupDelay`, `RoomCorrectionPlayback.withHeadroom`; a negative chain gain turns polarity over). `GroupSignalPath` builds the group's badges and per-DAC rows. Room correction reaches a group through `GroupRoomProfile` (profiles bound to the group's output UID) and `GroupGeometryProfile` (a profile of delays and levels from the drawing); measurement goes through `GroupMeasurement` and `GroupMeasurementOutput`. See [SPEAKER-GROUPS.md](SPEAKER-GROUPS.md).

### Mac Sound Output (beta)

`Driver/VespertineSound` is a Core Audio AudioServerPlugIn in plain C. It shows up to 8 outputs, each with a hidden capture device on the same clock, configured through one custom property on the plug-in object (`'vcfg'`, a list of uid, name, channels, labels and latency per output) and dropped after 20 s without a refresh. It applies the output's volume and mute as it writes its ring. The login-item helper (`Helper/`, Vespertine Sound Helper) runs `SystemOutputService`: it reads the app's snapshot (`SystemOutputSnapshot`, in `~/Library/Application Support/Vespertine Mac Sound Output`), refreshes the driver's configuration, and when an output starts running opens a `SystemOutputSession`. The session builds a private aggregate of the capture device (input only, drift-corrected to the group's leader) and the group's DACs; its I/O proc copies the input through a gain matrix (`SystemOutputRouting`, swapped with a one-cycle crossfade when the source changes between stereo and surround) into the group's room chain, or, for the upmix, through a worker thread running `StereoUpmixer` with the N-channel input delayed by the same amount. `GroupSessionResources` asks the helper to let go of a group before Vespertine plays it (`SystemOutputHandOff`, distributed notifications) and gives it back when it stops. See [MAC-SOUND-OUTPUT.md](MAC-SOUND-OUTPUT.md).
