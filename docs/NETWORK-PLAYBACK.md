# Network playback staging

SMB/NFS sources, including files added from Finder-mounted network volumes, are staged before decoding. This is mandatory playback buffering; the existing optional Network Cache/Keep Offline preference still controls persistent copies. A complete persistent copy is reused when available. With Network Cache enabled, completed staged bytes are adopted into it using an APFS clone (or a local copy), preserving persistent caching without a duplicate NAS read. Offline pins are retained.

Previously the engine started with 1.5 seconds of audio in its output ring and an additional eight seconds (at most 48 MiB) in `ReadAheadDecoder`. The independent library cache started copying after playback began and yielded when the ring was short. Only lossless PCM and DoP could switch to that completed copy without changing decoder state. Consequently the live decoder could still run dry.

## Ordinary tracks and the queue

**FLAC, WAV and AIFF of 12 MiB or more start on a prefix** (`NetworkStart`). The cache copies the first 4 MiB, the decoder opens through `NetworkPlaybackCache.Entry.inputSource()` (a guarded `SFBInputSource`: a read waits until its bytes are on disk and the copy fetches what is asked for first, so an unwritten range is never zeros or an early end of file), and the output starts once the copy's measured speed says the rest of the song will arrive before the playhead reaches it: never less than 2 MiB of lead, all of the rest when the copy has all but stopped. A slow link therefore waits for a part of the file in proportion to how slow it is, and never more than the old whole-file wait. The header readers that look at the file directly (`UndecodedFormat`) read through `PlaybackFile` for the same reason. The track is `streaming` while the copy completes (read-ahead thread, rebuffering as the fallback for a link that slows down), then switches to plain local reads. CUE tracks, MP4/ALAC (index at the end), MP3, APE and every other format below copy whole as before. `log show --predicate 'subsystem == "org.szeremeta.vespertine.player"'` shows `Starting <file> on the first N of M MB from the share after X ms` and `Opening <file> (ms): device, copy, probe, output, decoder, seek+converter, prefill` for each start.

Everything else: `NetworkPlaybackCache` copies the entire source before `SourceOpener.probe` or output starts. The decoder opens the local URL from its first frame; there is no decoder swap, resampling, or change to source bytes. Lossy codecs, integer PCM, DoP, CUE regions, IEC bitstreams and system-rendered Atmos retain their existing decoder/output paths. A network outage after staging cannot starve this track's decoder.

Once the current source is local, the engine copies the next queued source on a utility task. The next item is selected through the same queue provider as gapless playback, including shuffle/repeat and version selection. Queue changes replace the next lease. CUE regions sharing one source reuse that source. Compatible output formats still join through the existing ring and DoP marker alignment. If the next source has not arrived in time, there must be a wait at the boundary; no finite prefetch can guarantee a gapless boundary during an unlimited outage.

VIDEO_TS folder playback stages all IFO, BUP and VOB files as a set, preserving their names with local links. Caching only the entry IFO would leave the audio on the share. Disc images are copied as files; large SACD images with an explicit SACD area use the DSD path below.

## Large DSD

DSF, DSDIFF and identified SACD sources over 512 MiB use a sparse local file and guarded reads rather than waiting for the whole file. Startup first copies 16 MiB, opens/seeks the decoder, then waits for a lead at the decoder's actual audio position: two minutes at the raw DSD byte rate, at least 128 MiB and at most 1 GiB (clipped at EOF). At DSD64 stereo the minimum is roughly three minutes; the cap gives shorter reserves at extreme rates/channel counts. Startup latency depends on actual link throughput, so even the lead can take a long time on a very slow link, but it does not require a multi-gigabyte full copy.

FFmpeg receives a custom seekable AVIO source; native DST/SACD parsers use `PlaybackFile`. Every requested byte range waits until it is present on disk. An unwritten sparse range can never become zero-valued audio, corrupt-frame concealment or premature EOF. There is one remote copy reader per source; decoders read only local bytes. Demand ranges go first; background copying continues from the playback/seek position and eventually fills the rest. Temporary POSIX network read errors retry at the same byte offset while the local reserve plays; real EOF and local disk-write errors remain errors. A handle that keeps failing for a second (the share was mounted again after the link dropped, so the old handle is dead) is replaced by opening the file again at its path, if it is still the same size. When nothing at all has arrived for two minutes, the song fails with the share's "isn't answering" message, its waiting reads end and scans are no longer held back. Successful cache deliveries feed the existing share-health heartbeat so a busy NAS is not remounted just because staging replaced live decoding. Decoder seeks never reopen a separate live network stream. Once the source is complete, the engine clears its streaming state without replacing the decoder or disturbing conversion/filter/DoP marker state.

The current copy gets the connection before the next copy: for progressive DSD, next prefetch starts when the current copy finishes. A stall within the local lead does not interrupt audio. An outage longer than all buffered bytes, or a link persistently slower than the source's consumption rate, can still exhaust a progressive reserve. Existing lossless-position rebuffering remains as the final fallback, with the loading indicator. An absolute guarantee against an arbitrarily long outage requires the complete file before playback, which conflicts with progressive startup. This change does not claim that impossible guarantee for progressive DSD.

## Library scans make way

A share's reads, the song's and a library scan's (folder listings, tag reads), travel over one SMB session, so a scan's requests queue in front of the song's. `ShareIOGate` is the one place scans of a share wait. While a song needs the link, **no scan request starts**; those already on the wire finish. A song needs the link from the moment play is pressed (the share file is opened and its copy started right then, on a user-initiated queue, before the engine thread reaches the output) until its copy is local, whenever a decoder read is waiting on the copy, while a progressive DSD copy's reserve ahead of the decoder is under half, and while a live-streamed song's buffer is under a third full (or output is held for the network) until it is two thirds full again. Scans resume five seconds after the last of those stops, so a skip or a dip does not make them flap. A prefetched next song does not hold scans back until it becomes the current one. While a song streams live with a healthy buffer, scans still go one request at a time. Scans suspend between folder listings and between files, never in the middle of one. The copy itself runs on its own thread at user-initiated QoS; the scans' I/O queue is utility.

## Bounds, cleanup and loading

The transient cache reserves at most **8 GiB per process** across current, prefetched and still-finishing cancelled copies; it also checks for 64 MiB free-disk headroom, counting what the other copies in progress have yet to write (their files are sparse, so that space is not taken yet). Network Cache and Keep Offline copies leave 1 GiB of the disk free: a copy that does not fit is refused before anything is written, one that would take the last of it stops and removes its partial file, the queued copies are dropped and Settings › Network shows why. A source or DVD set exceeding that budget fails with the system's file-too-large error instead of silently reverting to live streaming. It never loads the whole source into RAM: the copy chunk is 1 MiB, in addition to the existing decoder/ring budgets. This hard limit also means an unusually large pair may have to wait/fail rather than exceed the reservation. Persistent offline copies remain separately governed by the existing settings.

Cache files live in the application's Caches directory under `Playback/<session UUID>`. Leases protect current/next files from deletion. Cancelled kernel network reads cannot always be interrupted, so their files and reservation remain until that read returns. Releasing the final lease deletes its file/session. On startup, advisory session locks permit removal of crash leftovers while protecting another running instance. The original music and metadata are never changed.

Opening the file on the share (and asking whether a Finder-mounted volume is a network volume) is a network call too, and the kernel does not give up on it when the share stops answering. Neither runs on the engine thread: each is asked on its own queue and the engine thread waits in 25 ms steps, so a skip or stop still gets through and ends the wait at once. The open itself finishes, or fails, in the background; the press-time warm-up and the engine thread share one open per file. The same holds for a seek on a song still arriving, and for an output change that keeps the song's decoder open: the seek reads where the share may not have sent anything yet, and the kept decoder's read-ahead may be waiting on it, so a skip, stop or another seek gives up on that wait (`NetworkPlaybackCache.cancellingReads`) instead of waiting as long as the share stays quiet.

Closing the file is a network call as well: SMB sends the server a close and waits for the answer, so on a share that has stopped answering `close` returns only when the share does (measured on an SMB mount: a close made while the server held its answers for 8 s took 8.3 s). A song's open file on the share is therefore never closed on the thread that lets go of the song. The copy hands it to a queue of its own (`NetworkPlaybackCache.closing`) when it is torn down or opens the file again, and the handle closes itself there whoever drops it; the cache also lets go of entries after its lock, not inside it. Before, a copied next song let go inside that lock held it until the share answered: the next press of play or skip waits for the same lock on the main thread, so the window froze, and a skip that dropped the song before it held the engine thread the same way. For the same reason nothing on the main thread makes a URL from a share's path without saying it is a file (`Track.fileURL`): Foundation otherwise asks the file system whether the path is a folder, which is a request to the share.

A share that is mounted and has stopped answering gives a song up after two minutes without a byte, or without its file opening (`NetworkPlaybackCache.defaultNoProgressLimit`), with "The share is mounted but isn't answering". Well before that, once a song that is waited for (its file opening, the start of its copy, a decoder's read of bytes not on disk yet) has had nothing from its share for 10 seconds (`NetworkPlaybackCache.defaultNoticeAfter`), `NetworkPlaybackCache.shareSilence` reports it, the engine snapshot carries it as `shareStalledSeconds` while the song is buffering, and the Inspector says "“Share” isn't answering. Still trying…" under "Buffering from the network…" (the banner says it once; both go when the share answers). It counts from the last byte or the start of the wait, whichever is later, so a slow share that keeps delivering never trips it, and a stall inside the local lead (the decoder reads what is already on disk) or a prefetched next song is no notice. The songs after it are not each waited for as long in turn: when the next one would be read from a share too, playback stops there with that reason; a next song with a copy on this Mac, or one that is not on a share, plays.

While a song plays, the engine thread prepares the one after it (gapless look-ahead), and on a share that can take longer than the output's buffer holds. That wait is not the playing song's buffering: it is not shown as one unless the output is nearly out of audio, the playhead keeps moving, and pause and resume are served during the wait (`serviceTransportWhileWaiting`) rather than after it. A pause or resume that comes while a song is still opening, or while a speaker group's output is being rebuilt, is applied when it opens: the last press wins and nothing sounds after a pause (`queuedTransportIntent`).

The full and compact brass transport replace their glyph with a small rotating ring during an initial network wait or rebuffering. Pressing it cancels the pending start. VoiceOver reports Cancel / BUFFERING; Reduce Motion freezes the ring. The same brass face, dimensions and shadow remain in use. A component snapshot is generated from the production SwiftUI component, not a mock HTML drawing.

## Validation and manual checks

`PlayPauseStateTests` runs the real engine thread against a simulated output (it counts the sound it is given) and a share the test slows, stalls or silences, and checks that the state, the playhead and the sound agree after quick play and pause presses; `NetworkStartTests` measures time to first audio on a throttled fake share (whole file first against a prefix) and decodes a WAV through the guarded input source while the share has gone quiet, byte for byte against direct decoding; it also covers the lead arithmetic. `NetworkPlaybackCacheTests` uses a throttled/stalling fake reader for complete-copy outages, progressive reserves, sparse-range waits/loading transitions and cancellation. It renders a whole staged PCM track through the real C ring/output context with zero underruns while the share is held, and compares guarded FFmpeg DSD→PCM and DoP output byte-for-byte with direct decoding. `NetworkPriorityTests` puts a scan and a play request on one slow shared link and checks the song is ready about as fast as with no scan, that scans pause and resume as described, and that pressing play starts the copy before the engine asks for it. Tests also cover budget reservations, live-session cleanup protection and DVD folder layout.

On a test library, try SMB and NFS, a Finder-added share, a normal FLAC/ALAC album with gapless joins, CUE tracks, DSD/DoP and DSD→PCM, seeking into a large DSD/SACD source, rapid skips, pause/cancel while loading, shuffle/Play Next changes and Keep Offline. Throttle the link before starting, then disconnect it after a normal track starts: that track should finish uninterrupted. For progressive DSD, distinguish a stall within its reserve from an outage longer than its reserve. Watch the loading ring and the signal-path/rate/bit-perfect indicators. No real DAC/physical loopback behavior was verified by the fake-reader tests.
